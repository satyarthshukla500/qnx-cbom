Check the cryptography of a QNX 8.0 image

A step-by-step tutorial with seven short steps. You build a QNX SDP 8.0 image, list every cryptographic component in it, check it, and compare two builds.

Steps

  1. 1Before you start
  2. 2Build the image
  3. 3Scan it
  4. 4Report and CBOM
  5. 5Look inside the running target
  6. 6Change it and compare
  7. 7CI and limits

1. Before you start

Step 1 of 7

What you will learn

  • how to find out which programs, libraries, keys and settings in a QNX SDP 8.0 image use cryptography;
  • how to read the result: UNSAFE, WARN, OK and the exit code;
  • how to ask the running target which libraries each process really loaded;
  • how to compare two builds and see a verdict change.

The tool is qnx-cbom. It lists the cryptography of an image (a CBOM, "cryptographic bill of materials") and checks it against a small set of rules. Everything it prints in this tutorial is real output from a real run.

What you need

  • QNX SDP 8.0.6, installed with the non-commercial licence, and its environment loaded with source ~/qnx800/qnxsdp-env.sh. Here ~/qnx800 is where it was installed.
  • Linux, or Windows with WSL2 (built and tested on Ubuntu 24.04 under WSL2).
  • Python 3.12 (standard library only; nothing to install).
  • QEMU 8.2.2 with qemu-system-x86_64, and git.

What you will not need

  • a QNX board or any hardware;
  • a network connection on the QNX target (the target runs in QEMU without a network);
  • root rights on the host, or mounting any disk image;
  • any extra Python package.

2. Build the image and find its parts

Step 2 of 7

mkqnximage is the SDK tool that builds a ready-to-run QNX image for QEMU. Make an empty folder for it and build with the default settings. The < /dev/null keeps the tool from asking questions, and | tail -6 only shows the end of its long output:

mkdir ~/qnx-image && cd ~/qnx-image
mkqnximage --type=qemu --build < /dev/null 2>&1 | tail -6
ls output
ls output/build | head -12
ls output/build/*.build

Three things in output/ matter for this tutorial:

  • ifs.bin is the boot image (the IFS). The files that start the system live in it, for example /proc/boot/libcrypto.so.3.
  • disk-qemu is the disk image. It holds a boot partition and two qnx6 file-system partitions, system and data.
  • output/build/ holds the build lists: ifs.build (what is in the boot image), system.build and data.build (what is in the two partitions). They also hold small files such as sshd_config as inline text.

To see where the OpenSSL library comes from, search the build lists:

grep -n "libcrypto" output/build/ifs.build output/build/system.build

The line says that libcrypto.so.3 goes into the boot image. At run time it is the file /proc/boot/libcrypto.so.3.

3. Scan the image and read the result

Step 3 of 7

Go to the tool folder and scan. --date fixes the "today" that end-of-life checks use, so you get the same answer on any day. Leave it out to use the real date.

cd ~/qnx-cbom
bin/qnx-cbom scan --ifs ~/qnx-image/output/ifs.bin --build-dir ~/qnx-image/output/build --date 2026-11-23 --text -; echo "exit code: $?"

Read it line by line

  • verdict: UNSAFE UNSAFE 2 WARN 4 OK 1: the overall verdict is the worst finding. Here there are 2 UNSAFE, 4 WARN and 1 OK finding.
  • files 217, ELF 168, crypto-linked ELF 19 (15 programs): 217 files were looked at, 168 of them are ELF programs or libraries, and 19 of those are linked to a crypto library (libcrypto, libssl or libqcrypto); 15 of the 19 are programs, the rest are libraries.
  • not analysed: skipped_outside_roots 2: two files named in the build lists point outside the folders the tool is allowed to read, so they were not opened. The tool says so instead of hiding it.
  • Each finding line is SEVERITY RULE subject - title. UNSAFE QCB-001 /proc/boot/libcrypto.so.3 means: the OpenSSL library in the boot image belongs to a series that upstream no longer supports (OpenSSL 3.0 ended on 2026-09-07). UNSAFE QCB-002 /system/bin/sshd means: the sshd program supports the post-quantum key exchange mlkem768x25519-sha256, but its sshd_config does not allow it.
  • WARN QCB-004 lines are keys with quantum-vulnerable algorithms (RSA, Ed25519, Ed448); WARN QCB-005 says qcrypto sends every algorithm to a plug-in that has no post-quantum algorithm.
  • exit code: 1: see the table.
Word or codeMeaning
UNSAFEThe item fails the stated baseline (a supported OpenSSL series; post-quantum key exchange where the build has it). A finding to act on, not proof of an attack.
WARNWeaker than ideal, or it could not be confirmed.
OKMeets the baseline.
exit code 0No UNSAFE finding.
exit code 1At least one UNSAFE finding.
exit code 2Bad input or usage (one line starting qnx-cbom: error:, never a traceback).

Optional: read the partitions from the real disk image

By default the files of the system and data partitions are taken from the build lists. With --disk the tool reads the qnx6 partitions of the real disk image itself (read-only, nothing is mounted):

bin/qnx-cbom scan --ifs ~/qnx-image/output/ifs.bin --build-dir ~/qnx-image/output/build --disk ~/qnx-image/output/disk-qemu --date 2026-11-23 --text -; echo "exit code: $?"

The verdict is the same. The file counts are higher. Most of the extra files are 91 hard links to one program (the build lists mark them as links, so the list scan does not count them as files), and two more are files whose list sources are outside the folders the tool may read.

4. Open the report and the CycloneDX file

Step 4 of 7

One scan can write several files. Write the scan file, the CycloneDX file and the HTML report together:

bin/qnx-cbom scan --ifs ~/qnx-image/output/ifs.bin --build-dir ~/qnx-image/output/build --date 2026-11-23 --json ~/scan.json --cbom ~/bom.cdx.json --html ~/report.html --text /dev/null; echo "exit code: $?"

The exit code is 1 again, because the verdict is still UNSAFE. Now look at what you made:

cd ~
python3 -c 'import json; b=json.load(open("bom.cdx.json")); c=b["components"]; print(b["bomFormat"], b["specVersion"]); print(len(c), "components"); print(sorted({x["type"] for x in c}))'
grep -o "<h2[^>]*>[^<]*" report.html | sed "s/<h2[^>]*>//"
  • report.html is for people. Open it in a browser (it is one file and loads nothing from the network). Each finding shows its evidence, a fix, the source the rule rests on and the date that source was read, and what could not be verified. You can filter and search the findings.
  • bom.cdx.json is for other tools. It is a CycloneDX 1.6 bill of materials: the image itself, each crypto-linked program and library, and each key, certificate and algorithm named in the configuration as a cryptographic-asset.
  • scan.json is the scan file. You need it in step 7 to compare two scans.

Check your work

The scan command prints (the text summary went to /dev/null, so only the exit code shows):

exit code: 1

The CycloneDX summary:

CycloneDX 1.6
42 components
['application', 'cryptographic-asset', 'library']

5. Look inside the running target

Step 5 of 7

A file scan shows what is in the image. It cannot show which library a process really loaded: for example a LD_LIBRARY_PATH setting can put a different libcrypto.so.3 in front of the image's one. For that there is a small program, the probe, that runs on the target. It only reads: for each process it opens /proc/<pid>/as and asks for the memory map (the same calls pidin uses).

Build it with qcc for both targets:

cd ~/qnx-cbom
make -C probe 2>&1 | tail -6
ls probe/build/x86_64 probe/build/aarch64le

About the next outputs. Booting the image in QEMU is slow and needs extra setup, so this step shows the output of the committed run in evidence/lab-stock-console.txt instead of repeating it. To repeat it yourself, run demo/run-demo.sh from the repository folder: it builds the probe, boots two lab images in QEMU and prints the scans.

On the target the probe prints one line of JSON between CBOM-BEGIN and CBOM-END lines (the end line carries the length and a checksum, so a console capture can be checked). From the committed run:

Output on the QNX target (committed run)
=== probe 1: image library in use
CBOM-BEGIN
{"schema":"qnx-cbom-probe/1","probe_version":"0.1.0","target":{"sysname":"QNX","release":"8.0.0","machine":"x86pc"},"sca
CBOM-END len=864 crc32=a7cfe74c

The JSON line is long, so here is the capture of that run, evidence/probe-stock.txt, in readable form. You can run this on your copy of the repository:

python3 -c 'import json; t=open("evidence/probe-stock.txt").read(); j=json.loads(t.split("CBOM-BEGIN\n")[1].split("\nCBOM-END")[0]); print("scanned", j["scanned"]); [print(p["name"], [(l["soname"], l["version"]) for l in p["libs"]]) for p in j["processes"]]'
Output
scanned 20
/system/bin/random [('libqcrypto.so.1.0', None), ('qcrypto-openssl-3.so', None), ('libcrypto.so.3', '3.0.22')]
/system/bin/openssl [('libssl.so.3', None), ('libcrypto.so.3', '3.0.22')]

Read it like this: scanned is the number of processes looked at. Only processes that have a crypto library mapped are listed. The random program has mapped libqcrypto.so.1.0, qcrypto-openssl-3.so and libcrypto.so.3, and that libcrypto.so.3 is OpenSSL 3.0.22. The openssl program has mapped libssl.so.3 and the same libcrypto.so.3. In the full JSON every library also has its path, released date and pq_capable (whether the file contains post-quantum algorithms).

Read it as a file: /dev/cbom

With -s the probe stays running as a QNX resource manager and appears as the file /dev/cbom. Any program can read the report with cat. Only root can read it, because the report lists every process that uses crypto. From the committed run:

=== cat /dev/cbom (first 400 bytes)

=== read twice: both are complete JSON
=== read twice: both are complete JSON

The first lines show the file (nr--------, owned by root) and the start of its JSON. Reading the file twice gave the same length both times (577 bytes), and both reads were complete JSON.

Merge it into the scan

Give the capture to the scan with --runtime. The repository holds the capture of that run, evidence/probe-stock.txt, so you can do this without booting anything:

bin/qnx-cbom scan --ifs ~/qnx-image/output/ifs.bin --build-dir ~/qnx-image/output/build --date 2026-11-23 --name stock-image --runtime evidence/probe-stock.txt --json ~/runtime.json --text -; echo "exit code: $?"

Compare with step 3: there is a new line runtime: 2 processes map crypto libraries ... and a new finding, QCB-007: a running process loads the OpenSSL library that is past upstream end of life. The verdict was already UNSAFE; now there is proof that the library is really in use.

6. Change something and compare

Step 6 of 7

The repository can build an upgraded lab image from a copy of the stock project (demo/build_after.sh): the OpenSSL libraries are replaced by an OpenSSL 3.5.9 build, and sshd_config lists mlkem768x25519-sha256 first. demo/run-demo.sh builds it, boots both images, runs the probe and scans both. It is a lab build in QEMU, not a shipped fix.

The scan files of that committed run are in evidence/. Compare the two with diff. It needs only Python:

cd ~/qnx-cbom
PYTHONPATH=src python3 -m qnxcbom diff evidence/before.json evidence/after.json; echo "exit code: $?"

Read it

  • verdict: UNSAFE -> WARN: the overall verdict went from UNSAFE to WARN.
  • CHANGED QCB-001 ...: UNSAFE -> OK (and the same for QCB-002 and QCB-007): these three findings are fixed in the second scan.
  • LIBRARY ...: 3.0.22 -> 3.5.9: the version of libcrypto.so.3 changed.
  • result: no new problems and exit code 0: nothing in the second scan is new or worse.

The WARN findings that remain are the classical keys and qcrypto. They stay because this change does not touch them.

The upgraded image was also booted and an SSH login that asked only for mlkem768x25519-sha256 succeeded. Lines from the committed run (evidence/lab-upgraded-console.txt):

On the QNX target (committed run)
100:debug1: kex: algorithm: mlkem768x25519-sha256
102:debug1: Sending command: echo LOGIN-OK
103:LOGIN-OK

Check your work

The diff prints exactly this:

new 0, gone 0, changed 3, library versions changed 1

7. Use it in CI, and know the limits

Step 7 of 7

Put it in CI

The exit codes are made for a build job. A scan fails the job when its exit code is not 0. A diff against a scan file you saved earlier (the baseline) fails when something got worse. Three real runs with the files from the earlier steps:

1. The same stock image scanned again with the runtime capture, compared with the committed baseline of the stock image: nothing changed, exit code 0.

bin/qnx-cbom diff evidence/before.json ~/runtime.json; echo "exit code: $?"
Output
verdict: UNSAFE -> UNSAFE
new 0, gone 0, changed 0, library versions changed 0
result: no new problems
exit code: 0

2. The upgraded image as the baseline and the stock image as the new scan: that is a build that got worse, and the exit code is 1.

bin/qnx-cbom diff evidence/after.json ~/runtime.json --text -; echo "exit code: $?"
Output
verdict: WARN -> UNSAFE
new 0, gone 0, changed 3, library versions changed 1
CHANGED  QCB-001 /proc/boot/libcrypto.so.3: OK -> UNSAFE
CHANGED  QCB-002 /system/bin/sshd: OK -> UNSAFE
CHANGED  QCB-007 /proc/boot/libcrypto.so.3: OK -> UNSAFE
LIBRARY  /proc/boot/libcrypto.so.3: 3.5.9 -> 3.0.22
result: worse
exit code: 1

3. Bad input gives exit code 2 and one line, no traceback:

bin/qnx-cbom scan --ifs ~/missing.bin --build-dir ~/qnx-image/output/build; echo "exit code: $?"
Output (the path is yours)
qnx-cbom: error: --ifs is not a file: ~/missing.bin
exit code: 2

Check your work

The three exit codes you should see are 0, 1 and 2, as in the outputs above.

Known limits

These are stated plainly, as in the repository README.

  • qnx6 reader. --disk was only tried on images made by mkqnx6fsimg / mkqnximage from SDP 8.0.6 (the stock image and small test images). It does not check the superblock checksums, does not use the second superblock, and ignores qnx6 features those tools do not produce (for example encrypted or snapshot volumes). If it cannot follow an image, that partition falls back to the build list, with a note in the report. The boot partition is not scanned from the disk. Without --disk the partitions come from the build lists only.
  • aarch64. The aarch64le probe compiles but has not been run: the SDK has no startup-qemu-virt, so no aarch64 image could be built.
  • Lab builds are not shipped fixes. The upgraded images are lab builds on QEMU: one with an OpenSSL 3.5.9 build of my own, one with the OpenSSL 3.5.4 port from qnx-ports (its libraries have the SONAME libcrypto.so.3.5; for the lab the file was installed under the name libcrypto.so.3). The post-quantum SSH login with the qnx-ports build worked only on a QEMU guest CPU without AVX2.
  • The sshd "Memory fault". On the stock image, sshd -t stops with "Memory fault" in QEMU. The core file shows it in sha512_block_data_order_avx2 (libcrypto 3.0.22), and the same command exits 0 when the guest CPU has no AVX2. It was not tried on real hardware or another QEMU version. It is not claimed to be a fault of the library or of QNX; the cause (emulated CPU or code) is unverified.
  • No real-time claim. Nothing about timing was measured, and none is claimed.
  • OpenSSL 3.0 after 2026-09-07. The SDP 8.0.6 package here is OpenSSL 3.0.22 (build of October 1, 2026), so QNX did ship 3.0 after the upstream end-of-life date. Whether later fixes are backported, and any support promise for 3.0, are unverified. The rules decide on 3.0 by the upstream date and list this as unverified.
  • Also. End-of-life dates for OpenSSL 1.0 and 1.1 were not read. SDP 8.0.6 has no key-encapsulation type in qcrypto, so QCB-005 has no in-place fix. /dev/cbom is read-only and was run on the QEMU target.
